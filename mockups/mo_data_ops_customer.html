How Mo Works
With Your Data

A plain-language walkthrough of the process behind each Mo intelligence module — what data it needs, where that data comes from, what operations are performed, and what appears on screen.

The end-to-end process — five steps from your SPINS export to decisions on screen
Step 1 SPINS Export BUILT Data Team
Step 2 Data Ingest Aevah — automated
Step 3 Feature Engineering Aevah builds intelligence tables
Step 4 Model Training & Scoring Aevah trains, scores, publishes
Step 5 Mo UI BUILT team sees decisions

Each analysis module follows the same pattern

For every intelligence module in Mo, we identify the required data inputs and their source (SPINS point-of-sale, ERP, or POS), perform the operations needed to prepare that data, train a focused model, and display the result as two distinct layers: projection data (what the model forecasts) and context data (the live actuals that explain why).

Operations on the data

Apply a guardrail that rejects regression windows where price moved more than 40% in a single week — typically a data artifact, not a real pricing event

Operations on the data
Normalize velocity to non-zero distribution weeks only — removing weeks when a SKU had no shelf presence eliminates false demand troughs from the training history
Compute rolling averages (4-week and 13-week) to smooth short-term noise while preserving trend signal
Build a 12-month seasonality index from category-level monthly raw averages (not model-estimated — directly observable from the data)
Flag promo weeks in the training history so the model learns baseline demand vs. promo-lifted demand separately
Train a separate forecast per SKU × retailer account — a SKU's velocity at Kroger is not a reliable predictor of its velocity at Target
Fall back to an exponential smoothing model for any SKU with fewer than 8 weeks of selling history

What external signals unlock
Separate BUILT price increases driven by strategy from those tracking broader food cost inflation (BLS CPI + commodity prices)
Explain demand seasonality driven by weather — c-store traffic drops in bad weather; protein bar velocity drops in winter (Open-Meteo)
Add forward-looking context to lagging SPINS actuals — "Recession probability 34%" alongside FRED consumer sentiment gives current reading + market expectation (Kalshi)
Track competitor velocity on Amazon 4 weeks before it shows in SPINS — early warning signal for distribution gains or promotional pushes (Helium 10 / Keepa)
Surface emerging flavor and format trends 3–18 months before peak SPINS volume — new product development input (Glimpse)
Integration pattern (all signals follow FRED model)
Server-side fetch with 1-hour cache — one API call per hour maximum; no per-user latency cost
API key stored in .env — endpoint returns graceful needs_key response if key is absent; UI degrades without crashing
Monthly / irregular signals forward-filled to weekly cadence to match SPINS data frequency
All signals rendered via the same Recharts ComposedChart pattern as the existing macro tile — no new UI framework required
Attribution required where specified by data provider (FRED: "Federal Reserve Bank of St. Louis")
Licensing rule: every external source must explicitly permit commercial redistribution before it appears in any customer-facing screen or Mo Chat response
Operations on the data
Fetch from external API on first request after cache expiry; subsequent requests within TTL return cached response
Join to SPINS weekly dates using nearest-neighbor match within ±4 days — handles irregular API cadences without gaps
Normalize to common index where needed (e.g., sentiment rebased to 100 = Jan 2024) for readable dual-axis charts
Filter out known anomalous spikes before rendering (e.g., gas price outliers during supply disruptions flagged via z-score)
