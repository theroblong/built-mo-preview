SPINS & Circana Pipeline Automation

Authors: Jason Brazeal, Rob Long Status: Draft — Sept 16, 2026 Scope: SPINS + CRX ingestion, validation gate, ML versioning

Goal: Rob drops a new SPINS or Circana extract into MinIO and Mo handles the rest automatically — for clean incremental updates. Structural changes (channel renames, schema additions, category changes) are flagged for human review before any data touches Druid. ML models retrain on new data without disrupting live predictions.

Non-goal: Full end-to-end automation without a human touch point. The validation gate is the permanent human-in-the-loop mechanism for structural changes — not a phase to eventually remove.

2Current State

The current workflow is fully manual. Brian (BUILT team) accesses the SPINS portal and drops the extract into the spins-landing bucket in MinIO. Rob retrieves it from MinIO and loads it into Druid; Jason can also pull it from MinIO for further processing. The ingest runbook (docs/SPINS_INGEST_RUNBOOK.md) is then run manually to rebuild built_filtered_weekly in Druid; ML scripts are re-run in sequence. No automation; no validation; no model versioning.

4Validation Gate

Every new extract passes through a validation script (MO_76, not yet built) before touching Druid. The script runs in <60 seconds by streaming the gzip without full decompression, and exits with one of two codes: GREEN (auto-process tonight) or HOLD (flag for human review).

The script compares the new extract against a known-good manifest — a small JSON file written to MinIO after each successful ingestion, capturing the validated set of channel names, column names, category codes, and expected row count range. The manifest is the diff anchor.

● GREEN — auto-process
  • All existing columns present; no new columns
  • All existing channel names present; none added or removed
  • All existing brand/category codes present
  • Row count delta within ±25% of expected (new weeks × active UPC count)
  • Date range extends cleanly from last ingested week; no gaps
  • File naming follows known pattern (All_items_extract_MMDDYYYY.csv.gz)
→ Ingest queued for that evening · ML retrain queues overnight
◎ HOLD — flag for review
  • Any channel name appears, disappears, or changes spelling
  • Column added or removed from the extract
  • New brand or category code not in prior manifest
  • Row count outside ±25% of expected range
  • Date gap detected (missing weeks between last ingested and new file)
  • File name doesn't match expected pattern
→ Alert sent to Rob/Jason with diff report · No Druid writes until approved
Known-good manifest (stored in MinIO after each successful ingest)
// spins-landing/manifests/manifest_20260809.json { "extract_date": "2026-08-09", "ingested_at": "2026-09-03T21:33:00Z", "row_count": 48291043, "week_count": 185, "columns": ["upc", "retailer", "channel", ...], "channels": ["FOOD", "DRUG", "MASS MERCH", "MULO W/ CONVENIENCE", ...], "brands": ["BUILT BAR", "QUEST", "RXBAR", ...], "wMAPE_at_ingest": 4.1, "model_version_active": "MO_53_20260809_20260904" }
◈ The channel rename failure would have been caught here. MULO + CONVENIENCE → MULO W/ CONVENIENCE is exactly a "channel name changed" HOLD condition. The diff report would have shown it before a single row touched Druid.

6ML Model Versioning

Core rule: never retrain in place. The model currently serving Mo's UI is frozen and read-only. Training always writes to a separate candidate slot. Promotion requires passing a validation gate against a holdout period.

Version ID format
"{model_id}_{data_cutoff_YYYYMMDD}_{train_date_YYYYMMDD}" Examples: MO_53_20260914_20260915 # E1 demand; data through Sept 14; trained Sept 15 MO_55_20260914_20260915 # E2a cannibalization; same data cutoff MO_17_20260914_20260915 # E2b elasticity; same data cutoff

7Druid Query Architecture

The critical separation: source tables are append-only and never overwritten; scoring output tables are versioned and swapped atomically on promotion. The Mo API never queries a scoring table by its versioned name — it resolves through a registry layer that always points to the current active version.

Druid ingestion spec for incremental appends

For new weeks of SPINS data: use appendToExisting: true with only the new date range in the ioConfig. Druid adds new segments without touching existing ones. The appendToExisting: false failure mode (silently drops unlisted columns) only applies to full rebuilds — which are now restricted to schema change events only.

// Incremental append — safe for clean extracts { "type": "index_parallel", "spec": { "ioConfig": { "appendToExisting": true, // append only — never overwrite "inputSource": { "filter": "week_ending >= {last_ingested_date}" } }, "tuningConfig": { "rollup": false } // preserve row-level grain } } // Full rebuild — only on HOLD-reviewed schema changes, after human approval // appendToExisting: false — requires all columns declared in spec (guard: compare to manifest)
