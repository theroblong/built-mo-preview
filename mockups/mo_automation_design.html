Pipeline Automation Design

Architecture for removing manual steps from the Mo data operations pipeline — replacing named individuals with Aevah-driven orchestration, file-watch triggers, per-stage smoke-test gates, and automated scoring publication.

DRAFT · 2026-08-25 · v0.1 — No changes implemented; design only
Overview

Automated pipeline chain

Five stages run in sequence. Each stage has a smoke-test gate. A failure at any gate halts the run and raises an alert — scoring tables from the prior successful run remain live until the new run completes cleanly.

Rollback guarantee: Each stage writes to a staging table or versioned artifact before promoting to the live query path. A gate failure means the prior version stays live — no partial writes reach Mo users.
Trigger layer

What starts a run

Three trigger types; the file-watch is primary. Aevah monitors the MinIO deposit bucket — when a new SPINS export lands, it validates the file header and row count before handing off to Stage 0. If no file arrives within the expected weekly window, the scheduled fallback fires to alert the BUILT data contact rather than run stale.

Trigger typeConditionAction
Primary
File-watch		 New file detected in MinIO deposit bucket with valid header (214 columns, expected date range) Validate → start Stage 0 · log run ID + file fingerprint
Fallback
Scheduled cron		 No new file within expected weekly window (e.g., Tuesday 09:00 local and no file since prior week) Alert data contact at BUILT · do not run stale data · log missed-window event
Manual
Admin override		 Explicit trigger via Aevah admin or CLI (e.g., for re-runs after a gate failure is resolved) Start Stage 0 with override flag in run log · same gates apply
Orchestration layer

Stage-by-stage design

Each stage is a shell-orchestrated script chain (same pattern as run_fpa_report.sh). Smoke-test assertions run after every stage. Gate failure halts the run immediately — subsequent stages do not execute.

STAGE 0 SPINS Ingest trigger: file-watch event
Scripts
  • SPINS ingest pipeline (OVERWRITE WHERE pattern)
  • Incremental watermark update
  • High-water mark log entry
What it does
  • Loads only new weeks (watermark-gated)
  • Appends to spins_full — never full overwrite
  • Records file fingerprint, row delta, max week date
Output
  • spins_full updated
  • Run log: ingest row count, date range, BUILT UPC count
Gate — pass conditions
✓ Row delta > 0 and within expected range (±30% of prior week)
✓ Max week_end_date advanced vs. prior run
✓ Distinct BUILT UPC count unchanged or growing
Gate — fail actions
✗ Halt run · alert · do not proceed to Stage 1
✗ Prior spins_full state preserved (no partial write)
⚠ Exception — MULO rows
▸ spins_full includes MULO CRMA rows — these are geographic aggregates, not retailer-specific rows. They must be ingested but are filtered out of all account-level queries downstream. Row counts in the gate check should account for MULO row volume being disproportionately large vs. a single retailer.
STAGE 1 Feature Engineering trigger: Stage 0 gate pass
Scripts
  • Q-series Druid SQL chain (QS1–Q22)
  • Runs in dependency order: seed tables → enrichment → comparison pools → event detection → PE features
What it does
  • Rebuilds built_filtered_weekly, built_enriched_weekly, comparison_pool_weekly
  • Assembles ml_training_features
  • Produces price_elasticity_training_features
Output
  • All intermediate Druid feature tables updated
  • Run log: row counts, null rates, date ranges per table
Gate — pass conditions
✓ ml_training_features row count within 10% of prior run
✓ Null rate on key feature columns below threshold (e.g., <5%)
✓ Date range covers expected new weeks
✓ QS1 gate: new UPC count plausible (not an order-of-magnitude jump)
Gate — fail actions
✗ Halt · alert · prior feature tables remain live
⚠ Exceptions — Q-series data rules
▸ MULO exclusion: MULO CRMA rows are excluded from all account-level feature tables (built_filtered_weekly, comparison_pool_weekly). FOOD and MASS MERCH RMA rows are used for account-level data. MULO is excluded from SKU View by default and must not appear in ml_training_features as a distinct retailer.
▸ QS1 data-maturity gate: New UPCs must have ≥8 weeks of post-launch data before entering active scoring via Q5. Fewer than 8 weeks → flagged to new_product_ramp_monitor, not ml_training_features. This is intentional — do not treat low new-UPC counts as a gate failure.
▸ Null focal pct_chg columns: Some feature columns have expected NULL rates by design (e.g., pct_chg fields are NULL for first observed week). Null-rate thresholds must be calibrated per column, not applied uniformly.
STAGE 2 Model Training trigger: Stage 1 gate pass · conditional on drift or schedule
Scripts (conditional)
  • P1 — Cannibalization classifier
  • P2 — Donor ranker
  • P3 — Event detector
  • P7 — Price elasticity model
  • P11 — Cannibalization rate model
Retrain conditions
  • New data window > N weeks since last train (configurable; default 4)
  • Feature drift detected: distribution shift on key inputs vs. training window
  • Manual retrain flag set in run config
  • If no condition met: skip training, use existing model artifacts
Output
  • Versioned model artifacts (classifier, ranker, elasticity — q10/q50/q90, rate model)
  • Training metadata: feature list, hyperparameters, data version, eval metric
Gate — pass conditions (if training ran)
✓ Model artifact written and readable
✓ Eval metric within acceptable bounds vs. prior artifact
✓ Base/promo coherence check passes (<25% violation rate)
Gate — fail actions
✗ Retain prior model artifact · alert · proceed to Stage 3 with prior model (flagged in run log)
⚠ Expected warnings — do not treat as errors
▸ LightGBM degenerate label warnings: Expected during donor ranker (P2) training when group sizes are small. Log and monitor for frequency increases, but do not halt on these warnings alone.
▸ Numeric dtype conversion: Several feature columns require explicit cast to float before model ingestion. This conversion is part of the training scripts (not a bug) — log the cast operations but do not treat them as gate failures.
STAGE 3 Scoring trigger: Stage 2 gate pass (or skip)
Scripts
  • P4 — Cannibalization scorer
  • P5 — Event assembler
  • P6 — New pack enrollment
  • P8 — Price elasticity scorer
  • P10 — Price event queue
  • P12 — Rate forecast
What it does
  • Scores all focal × donor × account × geography × window combinations
  • Writes to staging tables before promotion
  • Applies all guardrails ($/bar, ramp suppression)
Output (staging)
  • scored_cannibalization
  • scored_price_elasticity
  • cannibalization_rate_forecast_weekly
  • event_queue, price_event_queue
Gate — pass conditions
✓ Coverage: scored_cannibalization combo count ≥ prior run (or within −5%)
✓ Coverage: scored_price_elasticity UPC count within expected range
✓ No degenerate output: elasticity distribution not collapsed to a single value
✓ Forecast rows cover expected SKU × account combinations
Gate — fail actions
✗ Do not promote staging tables to live · prior scoring tables remain active · alert
⚠ Exceptions — expected scoring behavior
▸ ~48% cannibalization coverage is expected and correct: scored_cannibalization covers roughly 48% of focal×donor combos. Root cause is the Q5 data-maturity gate (≥8 post-launch weeks required). Do not treat sub-100% coverage as a gate failure — the gate checks for regression from the prior run's baseline, not absolute coverage.
▸ $/bar guardrail in P8 (price elasticity scorer): Observations where price moved >40% in a single week are rejected as likely data artifacts. These rejected rows will not appear in scored_price_elasticity — they are discarded, not scored at zero. Coverage shortfalls attributable to the guardrail are expected and should be logged separately from model-coverage issues.
▸ Ramp suppression in P4: Focal×donor pairs where the focal SKU is in the ramp period (flagged by Q9) are suppressed from scored_cannibalization. These pairs are not missing — they are intentionally excluded and visible in new_product_ramp_monitor.
▸ MULO excluded from all scoring outputs: No scoring table should contain MULO CRMA as a distinct retailer account. Any MULO rows that appear in scoring output are a data lineage error, not expected behavior.
▸ Positive elasticity at AHOLD and VS accounts: Known artifact — AHOLD positive elasticity is a CRMA geographic aggregate artifact; VS positive values reflect clearance lifecycle pricing. These are not model errors. Pinned test cases should not assert negative elasticity for these accounts.
STAGE 4 UI Validation trigger: Stage 3 gate pass → promote to live
Checks
  • Spot-check known UPC × account combos against expected value ranges
  • Assert Mo API returns non-empty responses for pinned test cases
  • Verify live Druid query paths return data (not empty [])
Test cases (pinned)
  • Cannibalization: 2–3 known high-confidence pairs
  • Price elasticity: 2–3 UPCs with established direction
  • Forecast: 1–2 focal SKUs with known velocity pattern
Output
  • Staging tables promoted to live query path
  • Run marked complete in run log
  • Run summary written (coverage stats, model versions, gate outcomes)
Gate — pass conditions
✓ All pinned test cases return expected value direction and plausible magnitude
✓ No API endpoint returns empty [] for test UPCs
Gate — fail actions
✗ Do not promote · alert with test case diff · prior live tables preserved
⚠ Pinned test case rules
▸ Use FOOD or MASS MERCH accounts only — never MULO: MULO is excluded from SKU View by default. Pinned test cases that reference MULO as a retailer account will return no data and produce false gate failures.
▸ Do not assert exact values — assert direction and range: Scored outputs fluctuate week to week as new data arrives. Pin to expected direction (e.g., elasticity ε < 0, cannibalization status = CANNIBALIZING) and a plausible magnitude band, not a specific number.
▸ AHOLD and VS elasticity exceptions: Do not include AHOLD or Value Shoppe accounts as pinned elasticity test cases — both exhibit positive elasticity due to data artifacts (CRMA aggregation and clearance pricing, respectively), not model errors.
Druid optimization

Options for reducing load times

Three distinct levers with different risk profiles. Pursue in priority order — Option A is low-risk and likely the largest single gain. Options B and C require benchmark data before touching any spec.

OptionWhat it doesImpactRiskPrerequisites
A · Priority 1

Incremental ingest watermark		 Load only new weeks via OVERWRITE WHERE week_end_date > <watermark> — never re-process full history High Low — already using this pattern for spins_full Watermark metadata store (can be a simple table or file); verify all downstream Q-series queries are window-safe
B · Priority 2

Segment granularity tuning		 Adjust Druid segment granularity (e.g., WEEK → MONTH) and partition by week_end_date to reduce scan scope on time-range queries Medium Medium — spec change requires re-ingest; must not break MULO exclusion logic (MULO CRMA rows must remain filterable at query time) or OVERWRITE WHERE pattern Baseline query-time benchmark per table; spec change review; re-ingest test on a copy; verify MULO rows remain correctly excluded from account-level result sets after re-ingest
C · Priority 3

Rollup / pre-aggregation		 Aggregate at ingest time (sum units/dollars at brand × week × geography) to reduce row count for summary queries Medium-high for summary views High — changes the data model; may break UPC-level queries, MULO exclusion (CRMA channel tag must survive aggregation), SKU-granularity feature engineering, and the $/bar guardrail which requires UPC-week-level price observations Full audit of all downstream queries; confirm UPC-level granularity is preserved; verify MULO channel tag survives rollup; confirm $/bar guardrail inputs are unaffected
Testing philosophy

Reliability and accuracy principles

No spec change without a benchmark
Any Druid spec modification must be preceded by a before/after benchmark on the same queries against the same data. If the change doesn't show measurable improvement, it doesn't go live.
Smoke gates run on every automated run
Assertions are not a one-time release check. They run every time the pipeline fires and are the primary reliability signal — not monitoring dashboards added later.
Rollback is always defined before go-live
Each stage must have a documented rollback path before automation is enabled for that stage. "We'll figure it out if it fails" is not a plan when Mo is live for BUILT users.
Degenerate output detection
Coverage drops >10% from prior run, elasticity distribution collapsed to a single value, or scored_cannibalization returning zero rows for known focal SKUs — any of these halt and alert, regardless of whether the underlying code ran without error.
New methods run in parallel first
Any new Druid optimization or ingestion method runs alongside the existing method on a copy of the data until output parity is confirmed. Parallel runs, not cut-overs, are how we validate.
Run log is the audit trail
Every run records: trigger type, file fingerprint, row deltas, gate outcomes, model versions used, and whether a retrain occurred. This log is the authoritative answer to "what changed between last week and this week."
