NULL in this field means no measured cannibalization rate for a pair, which should be treated as 0 (no cannibalization), not missing data.

Normalization & Transforms 5 entries
IDDecision / CaveatWhere it appliesWhyStatusDate
NRM-01
Numeric dtype conversion required before model ingestion
Several feature columns arrive as object/string dtype from Druid and must be explicitly cast to float before passing to LightGBM or quantile regression models. Conversion is built into training and scoring scripts.
 P1P2P7P8P11 Druid returns numerics as strings in some query paths. Silently failing here produces model errors that are hard to trace. Explicit cast + type assertion on load is the fix. Active 2026-08-25
NRM-02
$/bar normalization for cross-pack price comparison
ARP (average retail price) is normalized to price-per-bar using pack count before any cross-SKU price comparison, elasticity calculation, or competitive gap analysis. Raw ARP is never compared across pack sizes.
 Q14–Q17P7P8P10 A 12-pack at $14.99 and a single at $1.99 have the same $/bar (~$1.25). Without normalization, pack-size differences dominate the price signal and corrupt elasticity estimates. Active 2026-08-25
NRM-03
Outlier clipping applied to key velocity features
Extreme velocity observations (units/week far outside the normal distribution for a pack size) are clipped before model training. Specific clip bounds are set per SKU segment, not globally.
 ml_training_featuresP1P7 Outliers are often SPINS data artifacts (double-counted weeks, delistings with inventory clearance spikes). Clipping prevents these from skewing gradient boosting splits. Active 2026-08-25
NRM-04
STL seasonal decomposition: use raw monthly avg for UI charts, not STL output
STL seasonal index produces a July artifact in SPINS data. UI charts use compute_monthly_demand_index() (12-month raw average). STL CSV is generated for forecasting pipeline use only — never fed directly to client-facing charts.
 forecast pipelineTrends suiteDemand Velocity STL July artifact inflates or deflates the seasonal index for July in a way that doesn't match observed SPINS seasonality. Raw monthly averaging is more accurate for the Wellness & Nutrition Bars category. Active 2026-08-25
NRM-05
Absolute $ promo value used (not % promo depth) in promo lift features
Promo feature uses absolute dollar discount amount, not percentage depth. This was confirmed as the stronger signal in MO_53 ablation — percentage depth was demoted.
 ml_training_featuresP1 promo features Absolute $ promo correlates more reliably with volume lift than % depth, likely because consumer response is anchored to shelf price, not percentage math. Confirmed in MO_53 28-feature set. Resolved 2026-08-25

Known Data Anomalies 6 entries
IDDecision / CaveatWhere it appliesWhyStatusDate
ANO-01
AHOLD positive price elasticity — CRMA artifact
AHOLD accounts show positive price elasticity in scored_price_elasticity. This is a known artifact of CRMA geographic aggregation — the aggregate smooths price variation in a way that inverts the estimated demand response. Do not cite AHOLD elasticity scores as valid in client artifacts.
 scored_price_elasticityPE suiteUI test cases CRMA aggregation across multiple retail formats in the AHOLD footprint creates a price-demand correlation inversion. Account-level RMA rows would be needed for a valid estimate. Monitor 2026-08-25
ANO-02
Value Shoppe (VS) positive price elasticity — clearance lifecycle
VS accounts show positive elasticity due to clearance pricing patterns — price drops coincide with the tail of a product lifecycle, when volume is also declining. The model correctly identifies the correlation; the economics are the anomaly.
 scored_price_elasticityPE suite Clearance lifecycle: a retailer marks down to clear inventory as a SKU exits distribution. Volume continues to fall even as price drops. This is real behavior, not a model error, but it should not be used to counsel a price decrease. Monitor 2026-08-25
ANO-03
STL July seasonal artifact in SPINS data
STL decomposition produces an inflated or deflated July seasonal index for the Wellness & Nutrition Bars category. The artifact is visible in the STL CSV but must not propagate to UI charts. Use compute_monthly_demand_index() (12-month raw average) for all client-visible seasonal charts.
 STL CSVTrends suiteDemand Velocity Likely caused by a SPINS data filing pattern in July (e.g., a common reset cycle or promotional blackout that is category-specific). Not a pipeline bug — the STL algorithm is fitting a real artifact in the input data. Active 2026-08-25
ANO-04
SPINS March peak (+30%) and December trough (−28%)
Category-wide seasonality for Wellness & Nutrition Bars shows a consistent March peak (New Year resolution carry-through) and December trough. Q1 is broadly high. This pattern is confirmed across multiple years and should be used to contextualize velocity and forecast numbers in UI.
 Demand VelocityTrends suiteForecast drawer SPINS data pattern confirmed via 12-month raw averaging. Use these anchors when explaining week-over-week velocity changes to BUILT users. Active 2026-08-25
ANO-05
Base/promo coherence violations — 24.24% rate before fix, now <25% threshold
Before MO_58, ~24.24% of training examples had incoherent base/promo unit relationships (e.g., base units > total units). MO_58 fixed the coherence logic. Gate threshold is <25% violation rate — if it rises above this in a future run, halt and investigate.
 ml_training_featuresP1Stage 2 gate Incoherent rows distort the classifier's understanding of the base/promo signal. MO_58 identified and fixed the root cause but the gate ensures regressions are caught on future data. Active 2026-08-25
ANO-06
Single-week extreme price moves (>40%) are SPINS data artifacts
ARP observations showing a >40% price change in a single week ($/bar basis) are treated as SPINS filing artifacts rather than real price events. These are rejected by the $/bar guardrail in P8 and not scored. They may represent retailer price-file corrections, temporary promotional display errors, or double-filed weeks.
 price_elasticity_weekly_featuresP8 Confirmed via spot review of flagged observations. No real retailer moves price by >40% in a single week in this category. The pattern is consistent with SPINS filing noise. Active 2026-08-25
Model Guardrails 5 entries
IDDecision / CaveatWhere it appliesWhyStatusDate
GRD-01
$/bar guardrail: reject price observations with >40% single-week move
Price elasticity scorer (P8) rejects any observation where ARP moved more than 40% in a single week on a $/bar basis. Rejected rows are logged but not scored — they are not set to zero elasticity.
 P8scored_price_elasticity These observations are SPINS filing artifacts (ANO-06). Including them corrupts the elasticity estimate for that UPC×account×window. Rejection preserves estimate quality. Active 2026-08-25
GRD-02
Ramp suppression: ramp-period pairs excluded from cannibalization scoring
Focal×donor pairs where the focal SKU is in the ramp period (≤8 weeks post-launch, flagged by Q9) are suppressed from scored_cannibalization. They appear in new_product_ramp_monitor instead. Not a coverage gap — intentional routing.
 P4scored_cannibalizationnew_product_ramp_monitor Cannibalization signal is unreliable during ramp — the focal SKU hasn't reached steady-state distribution, so TDP/velocity deltas reflect ramp dynamics, not true cannibalization. Active 2026-08-25
GRD-03
LightGBM degenerate label warnings are expected — not errors
During donor ranker (P2) training, LightGBM emits degenerate label warnings when group sizes are small (e.g., a focal SKU with only 1–2 donor candidates in the training window). These are logged but should not halt the pipeline.
 P2Stage 2 training Small groups are an inherent feature of the donor ranking task — not all focal SKUs have large donor pools. LambdaRank degrades gracefully on small groups; the warning is informational. Active 2026-08-25
GRD-04
QS1 data-maturity gate: ≥8 post-launch weeks required for active scoring
New BUILT UPCs must accumulate at least 8 weeks of post-launch sales data before entering ml_training_features and cannibalization scoring. UPCs with fewer than 8 weeks are routed to new_product_ramp_monitor. This is not a data quality failure — it is intentional.
 QS1Q5new_product_ramp_monitor Fewer than 8 weeks produces insufficient TDP and velocity signal for reliable cannibalization classification. The 8-week threshold was set empirically from MO_10 model development. Active 2026-08-25
GRD-05
built_tdp_share removed from model features — audit only
built_tdp_share (BUILT's share of category TDP) was tested as a model feature and found to hurt cannibalization classifier accuracy. Removed from ml_training_features after MO_53 ablation. Still computed and stored in audit tables for business review.
 ml_training_featuresP1MO_53 Feature demoted in the 28-feature definitive set. Including it degraded model performance — likely because TDP share at the category level introduces multicollinearity with individual SKU TDP features. Resolved 2026-08-25
Coverage & Scoring Behavior 4 entries
IDDecision / CaveatWhere it appliesWhyStatusDate
COV-01
scored_cannibalization covers ~48% of focal×donor combos — expected
The cannibalization scoring table covers approximately 48% of all possible focal×donor combinations. This is correct and expected — the root cause is the QS1 data-maturity gate (≥8 post-launch weeks). Coverage checks should measure regression from prior run, not absolute percentage.
 scored_cannibalizationStage 3 gate ~52% of potential pairs involve at least one SKU that has not yet met the 8-week maturity threshold. Coverage will grow over time as SKUs age. Not a bug. Active 2026-08-25
COV-02
FOOD and MULO channels are best for demos; demos should avoid dark retailers
Demo scenarios and smoke test cases should use FOOD-channel accounts (e.g., KROGER FOOD) or MULO-excluded multi-outlet views. Avoid demo-ing dark retailers (Winco, HEB, TJ's) — no category data exists, so the UI will show limited or no data.
 all Mo screensdemo scenarios Dark retailers have no SPINS coverage — they ship product but don't share point-of-sale data. Demo-ing them would show empty screens and undermine confidence in the platform. Active 2026-08-25
COV-03
Causal events and cannibalization rates must not be cross-linked in the UI
Price event → demand lift (Causal drawer, Price suite) and assortment → cannibalization rate (Rate Forecast, Cannibal suite) are separate mechanisms. The UI must never suggest that a price event caused a cannibalization rate change, or vice versa.
 Causal drawerRate ForecastMo Chat Cross-linking these two mechanisms would give BUILT users incorrect causal inference — e.g., attributing a rate change to a price promo when it was actually driven by a distribution gain. Kept strictly separate by design. Active 2026-08-25
COV-04
ML scoring tables must never be blended with live Druid context queries
Every Mo screen draws from two distinct sources: ML scoring tables (projection data, written by P-series in Stage 3) and live Druid queries (component/context data at render time). These have separate lineage and must never be merged or cited interchangeably.
 all Mo screensMo Chatautomation design Blending would mean showing ML projections labeled as observed actuals, or using observed actuals as if they were model outputs. Both introduce silent inaccuracy in a decision tool where cited numbers drive real $ decisions. Active 2026-08-25
Formulas & Metric Definitions 10 entries
IDMetricFormula / DefinitionWhere it appliesNotes & caveatsStatusDate
FML-01
Price elasticity (ε)
Demand sensitivity to own-price changes, estimated per UPC × account × window.
ε = ∂ log(units) / ∂ log(ARP) Estimated via quantile regression on 13-week rolling windows. Outputs: q10, q50, q90 bands.
 Q14–Q17P7P8scored_price_elasticity Log-log specification means ε is unit-free and directly interpretable as % demand change per 1% price change. Confound flags (promo weeks, new UPC periods) are included as covariates to isolate clean price signal. Cross-price elasticity (sensitivity to competitor price) estimated separately. See ANO-01/ANO-02 for AHOLD/VS sign anomalies. Active 2026-08-25
FML-02
$/bar normalization
Price per individual bar unit, enabling cross-pack-size price comparison.
price_per_bar = ARP / source_pack_count ARP = Average Retail Price (dollars) source_pack_count = bars per package
 Q14–Q17P7P8P10GRD-01 All cross-SKU price comparisons, elasticity estimation, and competitive gap calculations use $/bar. Raw ARP is never compared across pack sizes. The $/bar guardrail (GRD-01) uses this field: observations where $/bar moved >40% week-over-week are rejected as data artifacts. Active 2026-08-25
FML-03
Promo lift ratio
Ratio of incremental volume to base volume during a promoted week.
promo_lift_ratio = incr_units / base_units incr_units = units sold above baseline (SPINS field: Incr Units) base_units = baseline demand (SPINS field: Base Units)
 built_filtered_weeklyPromo Response suiteMO_73 Both incr_units and base_units come directly from SPINS — they are SPINS-modeled decompositions, not computed by Mo. A ratio >1 means promo drove more incremental volume than the baseline. Watch for the units_promo vs. Units % Promo distinction (NUL-05) — incr_units is not the same field as units_promo. Active 2026-08-25
FML-04
Promo depth (discount %)
Percentage price reduction during a promoted week relative to base price.
promo_depth_pct = (Base ARP − ARP) / Base ARP × 100 Base ARP = baseline (non-promo) ARP ARP = actual shelf price that week
 Q14Promo Response suiteMO_73 Used as a feature input, not a model output. Absolute $ promo value (Base ARP − ARP) is the stronger model signal than promo_depth_pct — confirmed in MO_53 ablation (NRM-05). Depth % is retained for UI display and interpretability. Active 2026-08-25
FML-05
TDP (Total Distribution Points)
Composite distribution metric combining breadth (% stores stocking) and depth (share of shelf) into a single weekly figure.
TDP = %ACV × (selling stores / total stores) × 100 [simplified] SPINS provides TDP directly. Mo uses: TDP, Any Promo and base TDP as separate feature inputs.
 built_filtered_weeklyQ1ml_training_featuresall suites TDP is the primary distribution signal in all Mo models. A growing TDP for a new SKU during ramp is expected and not a cannibalization signal (GRD-02). built_tdp_share (BUILT's share of category TDP) was tested as a feature and demoted — hurts model performance (GRD-05). Individual SKU TDP is retained. Active 2026-08-25
FML-06
Avg Weekly Units SPM (velocity)
Average units sold per store per week — normalizes velocity by distribution so high-distribution SKUs don't appear artificially stronger.
units_spm = Avg Weekly Units / Avg % ACV Selling SPINS field: Avg Weekly Units SPM (Stores Per Million — SPINS terminology for per-store velocity)
 built_filtered_weeklyDemand Velocity suiteSKU View SPM stands for "Selling Points per Million" in SPINS terminology — it normalizes by distribution points, not literally per million stores. Used in Demand Velocity suite as the primary velocity signal. Compare SKUs on SPM, not raw units, when distribution differs. Active 2026-08-25
FML-07
wMAPE (weighted MAPE) — conditional
Primary forecast accuracy metric. Weights errors by actual volume so high-volume weeks carry more weight than low-volume weeks.
wMAPE = Σ |actual − forecast| ─────────────────────── × 100 Σ actual Computed per-SKU × account × window. Conditional: exclude zero-actual weeks from denominator to avoid division by 0.
 P7P12forecast validationFP&A brief Conditional wMAPE (excluding zero-actual periods) was confirmed as correct for this dataset — weeks with zero actual sales are often delisting / out-of-stock artifacts that should not inflate the error metric. Standard MAPE (unweighted) is not used — it gives equal weight to small and large volume periods and is distorted by near-zero actuals. Active 2026-08-25
FML-08
Monthly demand index (seasonality)
12-month seasonal index used in UI charts and forecast decomposition. Not the STL output — a raw monthly average normalized to 1.0.
demand_index[month m] = avg_units[month m across all years] ───────────────────────────────── avg_units[all months] Function: compute_monthly_demand_index() Returns 12 values normalized around 1.0
 Trends suiteDemand VelocityForecast drawer STL decomposition is computed for forecasting pipeline use only — it produces a July artifact (ANO-03, NRM-04) that must not reach client-facing charts. This raw monthly index is the correct alternative for UI display. March ≈ +30% vs. annual avg; December ≈ −28% (ANO-04). Active 2026-08-25
FML-09
Cannibalization rate
Share of a focal SKU's sales volume that was shifted from a specific donor SKU (as opposed to net-new demand).
cannib_rate(focal, donor) = donor_unit_decline ────────────────── focal_unit_lift Where both are measured over the same pre/post event window. Bounded [0, 1]; values >1 clipped.
 Q3–Q5P11P12cannibalization_rate_forecast_weekly Rate is learned by P11 as a function of TDP, pricing, distribution, and assortment changes over the SKU lifecycle — it is not a static ratio but a time-evolving model output. P12 forecasts the rate 13 weeks forward. cannibal_rate_sum (aggregate across all donors) NULL → 0 fill is correct (NUL-02). Rate and causal lift must never be cross-linked in the UI (COV-03). Active 2026-08-25
FML-10
Incremental share (cannibalization scoring)
Fraction of a focal SKU's total lift that represents net-new demand (not shifted from donors). Complement of cannibalization rate.
incremental_share = 1 − Σ cannib_rate(focal, donor_i) for all scored donor_i = net-new fraction of focal lift not attributable to any donor
 scored_cannibalizationCannibalization suiteSKU Summary Displayed as the "incremental share" tile in the Cannibalization suite. A value near 1.0 means the focal SKU is growing the category; a value near 0 means it is mostly shifting existing demand. Mo Chat confirmed: 12pk = 94% incremental, cross-flavor single = 36% cannibalization (from MO_73). Active 2026-08-25

OPN-01
Per-column null-rate thresholds not yet defined
Stage 1 gate requires per-column null thresholds (NUL-03). These have not yet been defined — currently no automated null-rate check runs in the pipeline. Need to establish baseline null rates per column from current data and set alert thresholds.
 Stage 1 gateml_training_features Without per-column thresholds, null-rate regressions (e.g., a new SPINS extract with missing fields) will not be caught before scoring. Open 2026-08-25
OPN-02
Per-series drift detection not implemented
The model retrain condition (Stage 2) currently triggers on elapsed time or manual flag. Per-series feature drift detection — comparing the current data window's distribution against the training window — is not yet implemented.
 Stage 2 triggerP1P7 Without drift detection, a model trained on winter data may run stale on summer data without triggering a retrain, silently degrading forecast accuracy. Open 2026-08-25
OPN-03
Temporal / account holdout not yet implemented in PE model (MO_16)
Price elasticity model (P7) currently uses a random 80/20 train/test split. No temporal holdout or account holdout has been tested. This means the model may overfit to time-correlated patterns or specific retailer behavior.
 P7MO_16scored_price_elasticity Random splits can leak future information into training when the data has temporal autocorrelation (which price data always does). Temporal holdout is the correct validation approach for a time-series-derived model. Open 2026-08-25
OPN-04
AHOLD elasticity: should positive values be flagged or suppressed in UI?
AHOLD positive elasticity is a known CRMA artifact (ANO-01). Decision needed: should Mo suppress AHOLD elasticity scores from the PE suite display, flag them with a caveat, or display them as-is with a data source note?
 PE suitescored_price_elasticitySKU Retailer View Displaying uncaveated positive elasticity for AHOLD could cause BUILT to make incorrect pricing decisions (e.g., raising price expecting volume gains). Need a UX decision on how to surface this without cluttering the UI. Open 2026-08-25

Use: display "Recession probability: 34%" alongside FRED sentiment to add a forward-looking expectation alongside FRED's lagging actuals. Amazon BSR / keyword intelligence: competitor velocity proxy
Helium 10 ($99–$279/mo) and Keepa (€15/mo) provide Amazon Best Seller Rank trends and keyword demand data. BSR is a near-real-time velocity proxy for competitors — leads SPINS by 4+ weeks. Keepa is best for long-run price history; Helium 10 for live keyword demand and ASIN tracking. Only applicable for brands with meaningful Amazon presence.

Ingredient commodity prices: EIA diesel + Alpha Vantage + USDA ERS
Three free/low-cost sources cover CPG input costs: EIA diesel prices (distribution cost proxy, same FRED-style fetch), Alpha Vantage commodities (cocoa, sugar, dairy whey; free tier), and USDA ERS ingredient prices (sweeteners, dairy; free CSV bulk). Combined, these provide a cost-side signal to explain ARP trends independent of BUILT pricing strategy.
