Part 3 — The missing chunk

3 non-ML outputs

These are Druid queries and pipeline scripts, not trained models. They were absent from prior versions of this plan but are what Brian's team uses day-to-day. Brian named all three explicitly across multiple standups.

Druid query A — Base Velocity
Formula: Base Units ÷ # Stores Selling = non-promoted demand rate per store per week.

Why it matters: Brian asked for this in two separate meetings ("base units per store, that strips out the promo"). It's the number Connor's Excel process starts from. When velocity goes down as new items launch, base velocity isolates whether that's real demand erosion or a promo comparison artifact.

Source: built_filtered_weekly — columns base_units + stores_selling.
Feeds: Experiences 1 (Sales), 2 (Production context), 6 (BI baseline).
Format: Mo UI time-series view + CSV download, by SKU × retailer × time window (4w / 13w / 26w / 52w) with trend direction and YoY delta.
Lookup table B — Launch Ramp Benchmarks
What it is: Historical median velocity curves by segment / format / pack size — built from every BUILT launch in built_filtered_weekly grouped by First Week Selling. Answers: "Is this new item tracking above or below what a comparable launch looked like at this point?"

Why it matters: BUILT went from 3.5 to 7.5 SKUs in one year. New items don't have 52 weeks of history for E1. The ETS fallback handles forecasting; this benchmark answers "is the launch working?" — a different question.

Output table: launch_benchmarks — segment × format × pack × weeks_since_launch → median velocity (p25 / p50 / p75).
Feeds: Experience 7 (Marketing launch tracker), Experience 2 (Production ramp planning), Experience 1 (Sales velocity vs. benchmark per account).
Refresh: Quarterly. Data to build it is available in built_filtered_weekly today.
Report pipeline C — Demand Intelligence Report
What it is: Auto-generated after every SPINS refresh and model training run. Brian: "gets generated automatically every time data came in." Rob: "replaces Connor's manual Monday process."

Contents each run: (1) Forecast accuracy this cycle vs. prior vs. baseline — model is improving; (2) Base velocity trends — top movers up and down; (3) Cannibalization alerts — pairs where rate changed materially; (4) Distribution changes — SKUs that gained or lost ≥5 TDP points; (5) New item ramp status vs. benchmark; (6) Promo performance — lift this cycle vs. historical; (7) Forecast vs. actuals reconciliation — what was forecast, what happened, why the gap.

Two versions:
— Full (Connor / Chase / Jeff): HTML with drill-down, downloadable as PDF and section-level CSV. Audit trail embedded — every number traces to its source query and training run date.
— Executive summary (Brian / Bracken): One-page PDF. Structured as What / So What / Now What. No more than 5 items. Action-oriented.

Cadence: Every 4 weeks (SPINS monthly cycle).
Status: 22-script run_fpa_report.sh produces 50-page HTML (v2.2.0). Needs: auto-trigger wiring, base velocity section, executive summary version, delivery mechanism.

The Monday morning cadence

Brian: "If we get data on Monday, how will that affect what Connor does now versus what he used to do? I think that's enough of a use case." Here is that use case, step by step.

SPINS weekly export arrives → MinIO
Trigger event. File lands in object storage, ingest job kicks off automatically.
Druid ingestion runs — Q0 through Q9 query chain
~2–4 hours. Normalizes raw SPINS to built_filtered_weekly. Builds comparison pairs, feature table, rolling stats.
E1 Global retrains · E2a rates update
E1 LightGBM: ~30 min. E2a cannibalization: ~60 min. Both run after Druid ingestion completes.
Forecast, base velocity, and distribution change queries run
Reads fresh model output tables. Flags items with >15% forecast change vs. prior week as anomalies.
Demand intelligence report auto-generates
No manual trigger. Full report for Connor/Jeff; executive summary for Brian/Bracken.
Connor receives updated demand table (CSV) + report link
Replaces the spreadsheet Connor updates manually today. Same output shape as his current process so it drops into downstream systems.
Connor reviews → overrides if needed → locks version
Named, immutable snapshot (e.g., "2026-09 v3"). Planning experiences (Production, Procurement) lock to this version.
Production and Procurement see updated bars (masked)
From the locked version — no retailer detail. Converted to cases and pallets. Costco track updates separately on monthly CRX cadence.
Every 4 weeks — full demand intelligence report → Brian / Bracken
Accuracy trend over the training cycle. Executive one-pager to Bracken. Brian's team no longer does this manually.
